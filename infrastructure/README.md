# Development infrastructure workflow

## Stage 1: infrastructure provisioning

Stage 1 provisions the resource group, VNet/subnet, NSG, managed identity, ACR, MySQL Flexible Server, and Container Apps environment/application. Key Vault resources and the Key Vault module are excluded from this stage. MySQL credentials are generated by Terraform and configured as native Container Apps secrets. They are not hard-coded as plaintext in source, but Terraform state still contains sensitive values and must be treated as secret-bearing data.

This is a development provisioning baseline, not a production security baseline. The app has public HTTPS ingress, MySQL and ACR use public endpoints, and MySQL firewall rules are restricted to the current Container Apps outbound IPv4 addresses. The delegated subnet does not create Private Endpoints or private DNS. The NSG has no custom rules, and no NAT Gateway is provisioned.

## Stage 2: security hardening (planned)

After the provisioning flow and state are stable, reintroduce a managed secret store and rotation, address least-privilege database access, private networking where appropriate, app authentication/authorization and CORS, immutable image provenance, diagnostic log retention, and production recovery policies. Keep existing basic controls such as HTTPS-only ingress and managed identity; staging security work does not mean intentionally weakening them.

Log Analytics and platform diagnostic settings are intentionally not provisioned during Stage 1. Container Apps logs are streamed only; they are not retained in a workspace. The reusable `modules/log-analytics` module remains available for a later observability change. To enable centralized logs later, add that module back to the dev root and configure the Container Apps environment's `logs_destination` as `log-analytics` with its workspace ID.

## First-time Terraform state setup

**State warning:** the Azure backend blocks in `environments/dev/backend.tf` and `environments/dev/mysql-firewall/backend.tf` are currently commented out, so `terraform init` uses local state. The bootstrap creates the remote state storage account, but the dev roots are not currently configured to use it. Do not run an apply until the authoritative state has been identified and backend migration/recovery is planned. An empty state can cause Terraform to propose creating duplicates instead of managing existing resources; the local state backup may contain credentials. State files are git-ignored, but local files and backups still require protection.

For remote state, the dev backend expects the public Azure Blob Storage endpoint for `stmyappdev`, resource group `rg-tfstate-myapp-dev`, and container `tfstate`. On a fresh subscription, first run `terraform init` and `terraform apply` from `bootstrap/` using local state; then configure and initialize the dev backend with the correct state migration procedure. The bootstrap creates a normal public Storage endpoint; it does not create a Private Endpoint or private DNS zone. The identity running dev Terraform also needs `Storage Blob Data Contributor` on the state account/container.

If `terraform init` reports `lookup <account>.blob.core.windows.net: no such host`, that is a DNS resolution failure before Terraform can authenticate or inspect the container. Confirm the storage account name is correct and the bootstrap completed in the expected subscription. If the account exists, check that the machine's configured DNS resolver can resolve public Azure Storage hostnames and that outbound DNS/HTTPS is permitted. No private DNS configuration should be added for this public-endpoint design.

## Deploy, synchronize firewall, and migrate

Prerequisites: Terraform, Azure CLI signed into the target subscription, the correct authoritative Terraform state for both roots, and a backend image containing this repository's migration script. The helper uses `-auto-approve`; do not run it until the state/backend warning above is resolved and the plan is understood.

From the repository root, run:

```sh
bash infrastructure/scripts/deploy-dev.sh
```

The helper performs these steps in order:

1. Applies the dev infrastructure root.
2. Reads the deployed Container App's current outbound IP list from Terraform outputs.
3. Applies only the dedicated `mysql-firewall` Terraform root, reconciling per-IP MySQL firewall rules. No manual IP copy or second full infrastructure apply is needed.
4. Runs `npm run db:migrate` inside the Container App, after its egress is allowlisted.

For an infrastructure-only deployment before the new backend image is published, set `SKIP_DB_MIGRATION=true`; the placeholder image does not contain the migration command. When using automation, Terraform's usual `TF_CLI_ARGS_apply=-auto-approve` environment setting can disable interactive approval for both applies.

The firewall root has its own remote state key (`dev/mysql-firewall.tfstate`). Keep that state: it exclusively owns the generated MySQL firewall rules. Use this helper for future deployments so changed ACA egress IPs are reconciled and stale rules removed. Without NAT, ACA outbound IPs may change; a direct `terraform apply` of only the dev root will not synchronize firewall rules.

## Database contract

Terraform injects `DB_HOST`, `DB_PORT`, `DB_NAME`, and `PORT` as ordinary app settings and maps Terraform-generated MySQL administrator credentials to native Container Apps secrets exposed to the process as `DB_USER` and `DB_PASSWORD`. The credential values are sensitive in Terraform configuration but remain present in Terraform state. Do not commit generated credentials or state files. `DB_SSL=true` is set for Azure MySQL; Docker Compose uses `DB_SSL=false` for local MySQL.

Terraform creates the `guestbook_db` database. `app/database/schema.sql` contains an idempotent table migration. `npm run db:migrate` applies that schema. It is also mounted as the MySQL container's initialization script for a fresh local Compose volume.

The current dev database username is the MySQL server administrator account. This is a temporary Stage 1 shortcut only; replace it with a distinct least-privilege app user as part of Stage 2 before production.
